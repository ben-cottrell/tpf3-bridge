# TPF3 railway design

This is the repository-managed entry point, loaded by the project's AGENTS.md for
railway design tasks. It is not an installed personal skill or a new bridge API.

Read [the procedure](../RAILWAY_DESIGN_PROCEDURE.md) before planning or materially
changing a layout. Use its proportional workflow; a simple connection needs only
a brief record, while a coupled junction needs a spatial plan.

- Start a live design record from [the template](DESIGN_RECORD_TEMPLATE.md).
- Read relevant [pattern cases](PATTERNS.md), including their limitations.
- Consult [the handbook](../RAILWAY_DESIGN_GUIDE.md) for detailed native lessons.
- When changing this procedure, use the affected [regression cases](REGRESSION_CASES.md).

The designer owns topology, route priority, paired corridors, crossing order,
footprint and revisions. An implementation worker may fit within the current plan;
material changes return to the designer. This division does not require spawning
an agent, or require human approval for already-authorised design decisions.

Do not replace game fitting with fixed radius/gradient rules, treat accepted native
construction as design approval, or turn historical example dimensions into limits.
Current user scope and external tool review remain binding. Reference inspection
does not itself authorise construction. Review-only tasks remain review-only.
